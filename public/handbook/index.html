02 / HOW IT WORKS

สองเส้นทางข้อมูล
มาบรรจบที่รายงานเดียว

DiscoverySeed IP + SSH→Network devicesCDP / LLDP / VLAN→Topology snapshotข้อมูลล่าสุดขององค์กร

08 / DISCOVER YOUR NETWORK

เริ่มจาก Seed IP
สู่แผนผังเครือข่าย

  1. เลือกองค์กร → Discovery

    ตรวจว่า Worker ทำงานและเครื่องเข้าถึงเครือข่ายที่ได้รับอนุญาต

  2. กรอก Seed IP และ SSH

    ระบุ SSH username / password ที่มีสิทธิ์อ่านข้อมูลอุปกรณ์

  3. กำหนดความลึก 0–10 hops

    หน้าเว็บตั้งต้นที่ 3 ควรเลือกตามขอบเขตงาน

  4. กด “เริ่ม Discover Topology”

    ติดตามงานจนเสร็จ แล้วเปิด Topology

ผู้ดูแลต้องตั้ง DISCOVERY_ALLOWED_CIDRS ใน backend/.env ให้ครอบคลุมทั้ง Seed และอุปกรณ์ข้างเคียง แล้วเริ่ม Worker ใหม่

หนึ่งองค์กรมี Discovery ที่ active ได้หนึ่งงาน จำกัดเวลาทำงาน 15 นาที ระบบเก็บรหัสผ่าน SSH แบบเข้ารหัสและไม่แสดงกลับในหน้าเว็บ

09 / DISCOVERY PROGRESS

รู้ว่างานอยู่ขั้นตอนไหน

queued→running→completed
สถานะความหมาย / การดำเนินการ
queuedรอ Worker รับงาน หากรอนานให้ตรวจ Worker
runningกำลังเชื่อมต่อ SSH อ่านข้อมูลอุปกรณ์ เพื่อนบ้าน และ VLAN
completedเปิด Topology และตรวจผล รวมทั้งรายการอุปกรณ์ที่เข้าถึงไม่ได้
failedอ่านข้อผิดพลาด ตรวจ SSH / เส้นทาง / CIDR แล้วสร้างงานใหม่หลังแก้ไข
cancelling → cancelledรอ Worker หยุดงานจริง ถ้ายัง queued จะยกเลิกได้ทันที
หน้าเว็บดึงข้อมูลเป็นช่วง ๆ ทุก 5 วินาที ตัวนับอุปกรณ์ที่พบ / ล้มเหลว / รอค้นหาเป็นความคืบหน้าที่สังเกตได้ ไม่ใช่เปอร์เซ็นต์ของเครือข่ายทั้งหมด

10 / TOPOLOGY & VLAN

อ่านการเชื่อมต่อ
พร้อมบริบทของบริการ

แผนผังเครือข่าย

  • เลือกอุปกรณ์เพื่อดูรายละเอียดและพอร์ต
  • ลากอุปกรณ์เพื่อจัดตำแหน่ง ใช้ปุ่มซูมเข้า / ออก
  • ค้นหาชื่ออุปกรณ์ในตาราง และอ่านตาราง Links
  • กด Export JSON เพื่อเก็บข้อมูล Topology พร้อม Layout

VLAN inventory

  • ค้นหาด้วย VLAN ID, ชื่อ หรืออุปกรณ์
  • ดูชื่อ VLAN / Service แยกตามอุปกรณ์
  • กดชื่ออุปกรณ์เพื่อกรองตาราง VLAN ตามอุปกรณ์
  • ถ้าข้อมูลเดิมไม่มีชื่อรายอุปกรณ์ ให้ Discovery ใหม่เพื่อยืนยัน
Reset Topology ลบข้อมูลจริง: ลบ Snapshot และข้อมูล VLAN ทั้งหมดขององค์กรที่เลือก แต่คงประวัติ Discovery, Logs และ Reports ไว้ ระบบไม่ให้ Reset ขณะมี Discovery active

Topology เป็นภาพจาก Discovery ล่าสุด ไม่ใช่การตรวจสถานะอุปกรณ์แบบสดตลอดเวลา ส่วนตำแหน่งที่จัดบนแผนผังเก็บในเบราว์เซอร์

11 / FIND THE EVIDENCE

เริ่มตรวจเหตุการณ์
จากหลักฐานใน Log

  1. เลือกองค์กร → Log history

    ค้นหาด้วยข้อความหรือชื่ออุปกรณ์ที่เกี่ยวข้อง

  2. กำหนดวันเริ่มต้นและวันสิ้นสุด

    ตัวกรองครอบคลุมทั้งวันตามเขตเวลาของเบราว์เซอร์ แล้วกดค้นหา

  3. อ่านเวลา อุปกรณ์ ระดับความรุนแรง และข้อความ

    เทียบพอร์ตและชื่ออุปกรณ์กับ Topology ขององค์กรเดียวกัน

  4. เปิด Original log JSON

    ตรวจ Payload ต้นฉบับเมื่อจำเป็นต้องตรวจการส่งข้อมูลหรือรายละเอียดเพิ่มเติม

เวลาใน Log
ใช้เวลาจากเหตุการณ์ถ้ามีและอ่านได้ มิฉะนั้นใช้เวลารับเข้า ค่าเดิมยังเก็บอยู่ใน Payload
Ai Notify ปิดอยู่ก็ยังเห็น Log
การรับและเก็บ Log ทำงานต่อ ส่วนการวิเคราะห์และแจ้งเตือนถูกระงับ

12 / INCIDENT INGESTION

เชื่อม ElastAlert2
เข้ากับองค์กรที่ถูกต้อง

ผู้ดูแลใช้ Webhook key ขององค์กร และส่งเข้า FastAPI ที่ ElastAlert2 เข้าถึงได้ ไม่ใช่พอร์ตหน้าเว็บ Next.js

POST /webhook/incident
Content-Type: application/json
X-Webhook-Key: <organization-secret>
Idempotency-Key: <stable-incident-id>

{
  "device_name": "SW-CORE-01",
  "matches": [{
    "@timestamp": "2026-10-06T03:00:00Z",
    "message": "Interface Gi1/0/1 down",
    "severity": "critical"
  }]
}

ตรวจผลการรับเข้า

  • ตอบกลับ HTTP 202 พร้อม report ID
  • queued เมื่อเปิด Ai Notify หรือ suppressed เมื่อปิด
  • แต่ละ match กลายเป็นรายการ Log ที่ค้นหาได้
  • Retry เหตุการณ์เดิมต้องใช้ Idempotency-Key เดิม เหตุการณ์ใหม่ต้องใช้ Key ใหม่

ตัวอย่างโครงสร้างสำหรับอธิบาย ไม่ใช่ข้อมูลหรือ Secret ของระบบจริง

เริ่มตรวจการรับ Log โดยปิด Ai Notify ก่อน จากนั้นค่อยทดสอบ AI / Teams ตามขอบเขตที่ได้รับอนุญาต คู่มือเชื่อมต่อฉบับเต็ม: docs/elastalert-integration.md

03

พิจารณาแนวทางแก้ไข

รายงานขอให้ Ollama สร้าง RCA ภาษาไทย ให้ทีมตรวจความถูกต้องก่อนลงมือกับอุปกรณ์

queued→running→completedหรือ failed / suppressed
completed ไม่ได้แปลว่าส่ง Teams สำเร็จ ต้องอ่านสถานะ Microsoft Teams ภายในรายงานแยกอีกครั้ง
ประเด็นสำหรับนำเสนอ ระบบใช้ Log กับ Topology / VLAN ที่มีอยู่มาประกอบการวิเคราะห์ ถ้าบริบทไม่ครบ ผลวิเคราะห์อาจมีข้อจำกัด

sentระบบได้รับผลตอบรับสำเร็จจาก Webhook ให้ตรวจข้อความในช่อง Teams เมื่อต้องยืนยันปลายทาง

ข้อความที่ส่งออกไปแล้วเรียกคืนไม่ได้ ระบบรอการส่งที่กำลังดำเนินการก่อนยืนยัน OFF และไม่ Retry งานที่ขัดจังหวะโดยอัตโนมัติเพื่อลดการแจ้งซ้ำ

16 / WALKTHROUGH

ตัวอย่าง: พอร์ตของ Core Switch down

สถานการณ์สมมติสำหรับสาธิต ไม่ใช่ผลการทดสอบหรือเหตุการณ์จริงในระบบ

ก่อนเกิดเหตุ

เลือกองค์กรและ Discovery เพื่อให้มี Topology / VLAN ล่าสุด เตรียม Worker และเปิด Ai Notify หลังตรวจ Ollama / Teams

รับเหตุการณ์

ElastAlert2 ส่ง Log ของ SW-CORE-01 และพอร์ต Gi1/0/1 เข้า API ด้วย Key ขององค์กร

ตรวจบนเว็บ

ค้นหา SW-CORE-01 ใน Log history เปิด Payload แล้วเทียบพอร์ตกับ Links ใน Topology

อ่านผลและส่งต่อ

เปิดรายงาน RCA ตรวจข้อเสนอแนะกับหลักฐานจริง ยืนยันสถานะ Teams และส่งออก PDF ให้ทีมปฏิบัติการ

แนวทางสาธิต เตรียมข้อมูลสาธิตที่ได้รับอนุญาตไว้ล่วงหน้า แสดงลำดับหน้าจอ Overview → Topology → Logs → Reports เพื่อเล่าเหตุการณ์ต่อเนื่อง

17 / TROUBLESHOOTING

หาจุดติดขัดตามอาการ

อาการตรวจอะไรเป็นลำดับแรก
เปิดเว็บไม่ได้Web ขึ้น Ready หรือยัง? ตรวจพอร์ต 3000 และ URL
เข้าเว็บได้ แต่ Login / โหลดข้อมูลไม่ได้API พอร์ต 8000, PostgreSQL healthy และ BACKEND_URL ใน .env.local
ไม่เห็นข้อมูลที่คาดไว้องค์กรที่เลือก สิทธิ์สมาชิก และตัวกรองวันที่ / อุปกรณ์
Discovery ค้าง queuedWorker ทำงานหรือไม่ และมีงาน active ขององค์กรอยู่หรือไม่
Discovery failed / พบอุปกรณ์ไม่ครบSeed IP, SSH, เส้นทางเครือข่าย, CIDR, depth และรายการ failures
รายงาน suppressedAi Notify ปิดอยู่ หรือถูกปิดระหว่างทำงาน การเปิดใหม่ไม่ Replay
Analysis failedOllama URL, model ที่โหลดไว้ และการเชื่อมต่อจากเครื่อง Worker
รายงาน completed แต่ Teams ไม่เข้าดู notification status ตรวจ Webhook / ปลายทาง / เครือข่าย
Webhook ถูกปฏิเสธใช้ Backend URL และ X-Webhook-Key ล่าสุดขององค์กรนั้นหรือไม่

เมื่อส่งเรื่องให้ผู้ดูแล ระบุเวลา องค์กร Job / Report ID และข้อความผิดพลาด โดยไม่แนบรหัสผ่านหรือ Webhook key

18 / OPERATOR REFERENCE

เปิดบริการแยก และปิดอย่างถูกวิธี

ใช้จาก D:\astar-v1 หลังฐานข้อมูลพร้อม โดยเปิดแต่ละบริการใน PowerShell คนละหน้าต่าง

1 / API

backend/.venv/Scripts/python backend/db.py
backend/.venv/Scripts/python -m uvicorn main:app --app-dir backend --host 127.0.0.1 --port 8000

2 / Web

npm.cmd run dev -- --hostname 127.0.0.1 --port 3000

3 / Worker เมื่อพร้อมรับงาน

backend/.venv/Scripts/python backend/worker.py
ปิดระบบ: กด Ctrl+C ในหน้าต่างที่รันแต่ละบริการ ถ้าต้องการหยุดฐานข้อมูลต่อ ให้รัน docker compose --env-file backend/.env stop postgres การปิดแท็บเว็บไม่หยุดบริการ

คำสั่งเหล่านี้ใช้กับบริการที่เปิดใน Terminal หากเริ่มเบื้องหลัง ให้ผู้ดูแลหยุดเฉพาะโปรเซสของบริการนั้น อย่าใช้ down -v เมื่อต้องการเพียงหยุดระบบ เพราะจะลบ Volume ข้อมูล

19 / FIRST-TIME SETUP

เตรียมเครื่องครั้งแรก

ตามข้อกำหนดโปรเจกต์: Node.js 20.9+, Python 3.11+ และ Docker Desktop ที่เปิด Engine แล้ว

cd D:\astar-v1
npm.cmd ci
python -m venv backend/.venv
backend/.venv/Scripts/python -m pip install -r backend/requirements.lock.txt
backend/.venv/Scripts/python backend/setup_local.py
docker compose --env-file backend/.env up -d postgres
# รอให้ postgres เป็น healthy
docker compose --env-file backend/.env ps
backend/.venv/Scripts/python backend/setup_local.py --admin

ค่าที่ผู้ดูแลต้องเตรียม

  • DATABASE_URL — การเชื่อมต่อ PostgreSQL
  • DISCOVERY_ALLOWED_CIDRS — เครือข่ายที่อนุญาต
  • OLLAMA_URL / OLLAMA_MODEL — ปลายทางและโมเดลที่โหลดแล้ว
  • TEAMS_WEBHOOK_URL — ใน backend/Notify.env หรือค่าไม่ว่างใน backend/.env
  • BACKEND_URL — ใน .env.local สำหรับ Next.js

setup_local.py สร้าง config และคีย์เข้ารหัสสำหรับการติดตั้งใหม่ โดยไม่เขียนทับ config หรือ Admin ที่มีอยู่ เก็บฐานข้อมูลและคีย์เข้ารหัสในชุดสำรองข้อมูลด้วย หลังแก้ค่า Worker ให้เริ่ม Worker ใหม่

การติดตั้งบน Ubuntu / ใช้งานจริง ให้ใช้ docs/ubuntu-production.md ซึ่งครอบคลุม HTTPS, APP_ORIGIN, COOKIE_SECURE และการแยกบริการ

20 / PRESENTATION GUIDE

จัดเรื่องเล่าให้จบใน 12 นาที

ช่วงหัวข้อที่ใช้ประเด็นพูด
1 นาทีเริ่มต้น + ภาพรวมทำไมทีมต้องเห็น Log และบริบทเครือข่ายร่วมกัน
2 นาทีระบบทำงานอย่างไร + บทบาทข้อมูลเดินทางอย่างไร และใครดูข้อมูลองค์กรใดได้
3 นาทีDiscovery + Topology + VLANเตรียมบริบทก่อนเกิด Incident และตรวจผลค้นหา
3 นาทีLogs + Reports + Teamsตรวจหลักฐาน อ่าน RCA และแยกสถานะส่งแจ้งเตือน
2 นาทีตัวอย่างหนึ่งเหตุการณ์เล่าการใช้งานตั้งแต่พอร์ต down จนส่งต่อให้ทีม
1 นาทีแก้ปัญหา + สรุปขั้นตอนประจำวันเลือกองค์กร → ตรวจบริบท → ตรวจเหตุการณ์ → ยืนยันผล
สำหรับอบรมผู้ใช้งาน ให้เพิ่มหัวข้อ Login, Export และคำสั่งเปิดระบบ สำหรับผู้ดูแล ให้เพิ่ม Clients & users, Webhook และการตั้งค่า
สคริปต์ปิดท้ายที่นำไปปรับใช้ได้ “Ai Notify ทำให้ทีมเข้าถึงข้อมูลเหตุการณ์และบริบทเครือข่ายในที่เดียว ขั้นตอนสำคัญคือเลือกองค์กรให้ถูก ตรวจข้อมูลต้นทาง และยืนยันทั้งผลวิเคราะห์กับผลส่งแจ้งเตือน”
